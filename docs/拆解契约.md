## 1. 目标与范围

把「信息拆解」做成 job3.0 工具箱的新模块：粘贴一段原始材料（文本/JSON），系统自动完成
**解析 → 事实拆解 → 洞察生成 → 报告合成** 四段流水线，每段之间由人工闸门把关，最终产出
可溯源、可导出的结构化拆解结果。

### 1.1 MVP 边界

| 项 | MVP（本期） | 二期 |
|---|---|---|
| 输入 | 粘贴文本 / JSON | 亚马逊链接自动抓取、文件上传 |
| 拆解流程 | 4 段 + 3 闸门 | 按需扩展段落 |
| 人工干预 | 闸门确认 / 重生成 / 重跑 | 补源重抓、冲突三选一裁决 |
| 输出 | 驾驶舱视图 + Markdown 导出 | PDF / 数据包导出 |
| 用户 | 单机本地 | 多角色权限 |

### 1.2 两条铁律

1. **前端只读契约**：前端不存自己的结论副本，只渲染后端产出的契约（contract）
2. **后端唯一写契约者**：任何人的决定（确认/重生成）都落成 decisions 记录，可审计

## 2. 术语

| 术语 | 含义 |
|---|---|
| 任务 task | 一次拆解从提交到完成的完整流程实例 |
| 契约 contract | 某一段流水线产出的结构化数据（facts + inferences + meta） |
| 事实 fact | 从原始材料中拆出的客观条目，带原文锚点 anchor |
| 推断 inference | 基于事实生成的结论，必须引用事实 ID |
| 闸门 gate | 需要人工确认的停靠点（A/B/C） |
| 版本 version | 契约每次重跑 +1，前端显示「待重跑」而不是悄悄改数字 |
| 状态 status | 契约状态：auto_ok / needs_human / human_approved |
| 置信度 confidence | C1 未验证(红) / C2 单源推断(黄) / C3 双源或原文直接命中(绿) |

## 3. 拆解流程（4 段 3 闸门）

```
[粘贴原始材料]
    → S0 输入解析（目标识别 + 材料结构化）
    → 🔒 闸门A：Brief 确认（拆解目标对不对）
    → S1 事实拆解（拆成事实条目，每条带原文锚点）
    → 🔒 闸门B：事实清单确认（标记 错/缺/对）
    → S2 洞察生成（六要点：卖点/定价/风险/机会/人群/建议，每条引用事实 + 置信度）
    → 🔒 闸门C：结论确认
    → S3 报告合成（驾驶舱数据 + 导出）
    → DONE
```

### 3.1 每段职责

| 段 | 输入 | 输出 | 闸门 |
|---|---|---|---|
| S0 输入解析 | 原始文本/JSON | 拆解目标 brief + 结构化 source_meta | A（确认目标） |
| S1 事实拆解 | 已确认 brief | facts 清单（每条带 anchor） | B（确认清单） |
| S2 洞察生成 | 已确认 facts | inferences 结论（引用 facts + C1-C3） | C（确认结论） |
| S3 报告合成 | 已确认 inferences | dashboard 数据 + 导出文件 | 无 |

### 3.2 改动传导

| 改动类型 | 举例 | 直接重算 | 联动复核 | 不受影响 | 前端表现 |
|---|---|---|---|---|---|
| A. 改输入 | 重新粘贴材料 | S0 | S1→S2→S3 | 无 | 流水线从头黄标 |
| B. 改事实 | 闸门B 标记某条事实错误 | S1 重拆 | S2→S3 | 无 | 该条红标 + 待重跑 |
| C. 新增证据 | 补充一段文本 | S1 增量 | S2→S3 | S0 | 事实列表刷新 |

## 4. 状态机（后端强制流转）

```
DRAFT(草稿) → BRIEF_REVIEW(闸门A) → DECOMPOSING(S1执行中)
→ FACTS_REVIEW(闸门B) → INSIGHTING(S2执行中) → INSIGHT_REVIEW(闸门C)
→ REPORTING(S3执行中) → DONE(完成)

任何状态可 → FAILED(失败，原因入 bad.md，可 RETRY)
```

前端只按状态渲染对应页面，不自行跳转。

## 5. 契约 Schema（通用）

```json
{
  "contract_name": "S1",
  "version": 1,
  "status": "needs_human",
  "created_at": "2026-09-01T10:00:00+08:00",
  "facts": [
    {
      "id": "F-001",
      "kind": "requirement",
      "content": "要求 3 年以上 Python 经验",
      "anchor": "第 3 段，第 2 行",
      "confidence": "C3"
    }
  ],
  "inferences": [],
  "meta": {
    "source_type": "text",
    "word_count": 1234,
    "errors": [],
    "data_gaps": []
  }
}
```

### 5.1 各段字段级定义

| 段 | facts 的 kind | inferences | meta 关键字段 |
|---|---|---|---|
| S0 | source_meta（材料概况） | brief：拆解目标 + 待回答问题 | source_type / word_count / target_question |
| S1 | requirement / info / entity（按内容分） | 分类/聚类说明 | data_gaps（拆不出的部分标 C1，不编造） |
| S2 | 无（只读 S1） | conclusion：六要点 usp/pricing/risk/opportunity/audience/action，每条 2-3 句论证 + evidence + 置信度 | confidence 分布 |
| S3 | 无 | 最终结论清单（已确认）+ meta.summary/sections/actions（执行摘要/分要点/建议） | 导出文件信息 |

### 5.2 六要点模板与 S3 报告结构

S2 按固定六要点输出洞察（LLM 与规则兜底同模板，材料未覆盖的要点标 C1 并写「材料未提及」）：

| 要点 type | 含义 |
|---|---|
| usp | 核心卖点 / 关键要求 |
| pricing | 定价与成本 |
| risk | 风险与短板 |
| opportunity | 机会与空间 |
| audience | 目标人群 / 适用场景 |
| action | 行动建议 |

S3 不再复制 S2，而是真合成一份报告，字段放在契约 meta 内：

- `meta.summary`：执行摘要（材料是什么 + 最重要结论 + 主要风险/机会）
- `meta.sections`：按要点分节论证（type/title/content/evidence）
- `meta.actions`：下一步行动建议（2-4 条）

导出 Markdown 结构：元信息 → 执行摘要 → 结论（按要点）→ 结论明细 → 事实清单 → 数据缺口 → 闸门确认记录 → 下一步建议。

## 6. 动作接口（4 类 8 个）

### 6.1 任务类

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/decompose/tasks` | 新建任务（粘贴内容 + 可选拆解目标） |
| GET | `/api/decompose/tasks` | 任务列表（状态筛选） |
| GET | `/api/decompose/tasks/{id}` | 任务详情 + 全部契约 |
| DELETE | `/api/decompose/tasks/{id}` | 删除任务（级联删除契约与决策，不存在返回 404） |
| GET | `/api/decompose/tasks/{id}/events` | SSE 进度订阅 |

### 6.2 闸门类

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/decompose/tasks/{id}/gates` | 待确认闸门列表 |
| POST | `/api/decompose/gates/{id}/decide` | 确认 / 重生成（结构化意见） |

### 6.3 动作类

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/decompose/tasks/{id}/rerun` | 从指定段重跑（version+1） |
| POST | `/api/decompose/tasks/{id}/export` | 导出 Markdown 报告 |

### 6.4 SSE 事件类型

| 事件 | 说明 |
|---|---|
| `thinking` | 某段执行中 |
| `output` | 契约片段产出 |
| `gate` | 到达闸门，等待确认 |
| `complete` | 任务完成 |
| `error` | 失败（含原因，入 bad.md） |

## 8. mock 层约定（前端先行关键）

- 路径：`src/api/decompose/mock.js`，与真实 API 同形状（函数签名一致）
- SSE 用定时器模拟事件序列（thinking → output → gate → complete）
- mock 层只覆盖业务演示场景；失败重试由后端测试通过异常注入验证，不作为用户可选场景：
  1. **正常完成**：一路绿灯跑完
  2. **闸门重生成**：闸门B 提交意见 → 重跑 → 版本对比
- 切换方式：`src/api/decompose/index.ts` 中由 `USE_MOCK` 选择 mock / real
- 验收标准：**2 个业务场景全部跑通** = mock 流程完成；失败恢复由后端注入异常的集成测试负责

## 9. 数据库表（后端阶段）

| 表 | 关键字段 | 说明 |
|---|---|---|
| decompose_tasks | id, name, state, version, created_at | 任务主表 |
| decompose_contracts | task_id, contract_name, version, status, body(JSON) | 每段一份，版本化 |
| decompose_decisions | task_id, gate, action, note, decided_at | 人的确认/意见留痕 |
| audit_log（可选） | who, when, what, before, after | 写操作审计 |

写入规则：每次写契约必须带 version（乐观锁）；闸门确认 = 事务（写 decisions + 更新 status + 触发下游）。
